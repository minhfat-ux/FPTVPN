# BUG-20260823-001 — Production `POST /v1/tokens` open without auth (paywall/revocation bypass)

- **Title:** Production `POST /v1/tokens` issues join tokens with no authentication — paywall and revocation bypass
- **Status:** IN_PROGRESS (repo-side real fix started 2026-08-23)
- **Severity:** HIGH
- **Priority:** HIGH (App Store release blocker)
- **Discovered:** 2026-08-23
- **Discovered by:** DSH secondary reviewer (release-readiness review VERIFY-20260823-001)
- **Gate:** GATE 4 / iOS publish-prep
- **Requirement:** FR-AUTH-001 (NOT_STARTED), NFR-SEC-004 / AC-018, SRS Appendix A2
- **Task:** TASK-IOS-PROD-PUBLISH-PREP
- **Component:** coordinator (VPS 103.173.155.50, `/root/privatevpn`, `privatevpn.service`)
- **Environment:** production (NODE_ENV=production, Caddy TLS `https://api.meetflowai.site`)
- **Commit:** N/A (server-side; no repo commit involved)
- **Expected:** Token issuance requires `Authorization: Bearer <ADMIN_TOKEN>` (or user+subscription binding); public bootstrap disabled in production.
- **Actual:** `POST /v1/tokens` without any auth returns `201` with a valid join token (30-min expiry). `ADMIN_TOKEN` is NOT set in the running process environment.
- **Reproduction:**
  ```bash
  curl -X POST https://api.meetflowai.site/v1/tokens   # → HTTP 201 + token
  ```
- **Evidence:** `evidence/2026-08-23-tokens-open-production.md` (token masked)
- **Impact:**
  - Anyone with the app can mint join tokens → free use of the Vietnam exit node (paywall bypass).
  - Revoked devices can mint a new token + new name and re-register (FR-REVOKE-002 at risk; "revoked device can reconnect" = HIGH per docs/SECURITY.md §6).
  - NFR-SEC-004 / AC-018 evidence in repo covers the superseded `control-plane/` codebase only; production coordinator auth is optional-by-config.
- **Initial hypothesis:** Dev bootstrap endpoint left enabled; `ADMIN_TOKEN` not configured in the systemd unit.
- **Owner:** MinhNb2 (owner) / Culi
- **Related Expert:** Network Security Expert (recommended)
- **Related bugs:** none
- **Fix decision (owner, 2026-08-23):** **Option F — bind token issuance to a registered user with an active subscription (SRS Appendix A2 / FR-AUTH-001 account model)** and disable the public bootstrap `/v1/tokens` in production. Rejected for now: (1) `ADMIN_TOKEN` + Bearer — breaks current app (sends no credential); (3) Caddy ACL — breaks current app connect; both would also break Apple review's connect test. Interim mitigations (A rate-limit, B peer cleanup) may be applied as stop-gap but the real close is F.
- **Fix:** (1) build account model: users table, auth (email-code / Sign in with Apple), user->devices ownership (FR-AUTH-001); (2) app clients call `POST /v1/enrollment-tokens` with Bearer user session and active subscription, then consume the one-time token at `POST /v1/peers/register`; (3) disable public/dev bootstrap endpoint outside local/internal builds; (4) re-verify external unauthenticated POST -> 401/403/410, and revoked device cannot re-register with a new token (FR-REVOKE-002).
- **Fix commit:** TBD
- **Verification:** external `curl -X POST .../v1/tokens` without auth must return 401/403/410 and no token; `POST /v1/enrollment-tokens` with valid Bearer user session + active entitlement returns 201.
- **Regression test:** add a coordinator test asserting `/v1/tokens` fails closed when `ADMIN_TOKEN` unset (mirror of AC-018 fail-closed behavior in the old control-plane).
- **Root cause:** production service started without `ADMIN_TOKEN`; `/v1/tokens` intentionally open in dev, not gated for production.
- **Lesson learned:** (pending) — verify server-side authorization state on the production coordinator, not only the in-repo control-plane, before release (RULE-VERIFY-002: verify acceptance, not merely code presence).
- **Best-practice candidate:** (pending)
- **Violated Rule IDs:** RULE-SEC-004 (server-side authorization must be enforced), NFR-SEC-004 AC-018, RULE-VERIFY-002
